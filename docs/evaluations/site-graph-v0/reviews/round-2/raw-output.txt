## P1

### P1-1 — The candidate-side top-1 concentration gate is compared against a differently-defined baseline number, and is inert on the Met side

`docs/evaluations/site-graph-v0/scripts/compare_candidate.py:399-406`, gate at `:619-633`; baseline definition at `scripts/build_baseline.py:297-317`; preregistered formula at `preregistration.json:92`.

`build_baseline.concentration()` computes `top_k_unique_record_concentration["1"]["ratio"]` as **union of distinct records on the top node / union of distinct records on any shared node** — which is exactly `preregistration.json:92`.

`compare_candidate.concentration()` computes `top_1_incidence_share` as `top / incidence`, where `incidence = sum(len(node_artifacts[t]) for t in ordered)` (`:399`) — a **sum with multiplicity**, not a union. Line `:631` then compares the second quantity to the first.

The numerators are identical; the denominators are not, and the gap is enormous on real data. `baseline-metrics.json:794-807` (Met side of `met__brooklyn`): `distinct_connected_records` = 14,392, `node_incidence_total` = 34,221, baseline top-1 = 11,417/14,392 = **0.7933**. A candidate reproducing the baseline exactly would score 11,417/34,221 = **0.3336** and pass `<= 0.7933 + 0.05` with 0.46 of slack. The Met-side concentration ceiling — the single gate protecting against "we reunified everything onto Thebes" — cannot fire. Brooklyn's ratio is 1188/1151, so the slack there is only ~0.009; the bug is silent precisely where it matters most.

Note HHI is *not* affected: `:404` and `build_baseline.py:303-306` use the same `sum(I²)/(ΣI)²`. Only top-1 diverges.

Nothing catches this. `test_concentration_is_gated_per_side_against_comparable_baseline` (`pipeline/tests/test_site_graph_v0_contract.py:465-477`) builds a fixture where every artifact links to exactly one shared target (`:217-230`, `_fraction(2, 2)`), so union == sum and the two formulas coincide. That is a rule-5 failure in the test: it asserts the gate fires, not that it measures the preregistered quantity.

**Fix:** in `compare_candidate.concentration()`, return `ratio(len(node_artifacts[ordered[0]]), len(set().union(*node_artifacts.values())))` for top-1 (keep `node_incidence_total` for HHI). Better: import and call `build_baseline.concentration()` on a link list projected from `candidate_links`, so there is one implementation (rule 4). Add a fixture in which one artifact carries two shared targets and assert the candidate's top-1 denominator equals the distinct-record count, not the incidence total.

### P1-2 — A candidate can relabel a frozen broad baseline node as specific, from its own self-attested hierarchy file

`compare_candidate.py:439` seeds `candidate_scope` from the committed baseline classes, then `:453-454` overwrites it for **every** candidate link — including links to targets that already exist in `baseline-node-scope.json` — with the candidate's own `scope_class`. `:345-355` derives the expected scope solely from the candidate-authored `hierarchy` (`child_ids`) and the crosswalk *vocabulary*; `:231-232` "verifies" that hierarchy by hashing the file the candidate itself supplied. There is no check anywhere that `link["scope_class"] == node_scope_by_target[target]` for a target present in both.

`type-crosswalk.json:15-25` exists to bind actual iDAI types to candidate types, but `compare_candidate.py` only ever reads `candidate_e55_vocabulary` (`:282-284`) and never `idai_gazetteer_actual_hyphenated_types` or `porter_moss_actual_representations`. So the binding half of the crosswalk is not executable.

Concretely: `idai:2042921` "Theben" is broad in the frozen baseline. A candidate declares a hierarchy node `{"target_id": "idai:2042921", "candidate_e55_type": "temple", "child_ids": []}`, marks its links `specific_candidate`, and `validate_inputs` passes. `candidate_broad` (`:606-610`) then excludes every record whose only shared target is Theben, `broad_change` goes negative, and the CONTINUE condition "broad-only share over X_m falls" (`preregistration.json:189`) is satisfied by relabelling alone, with zero research. That is the broad-to-specific inflation the whole contract exists to prevent, and `preregistration.json:223` explicitly prohibits "post-result per-node scope overrides" — a rule that exists only in that JSON string (rule 3).

`test_slice_leafness_cannot_override_complete_hierarchy_context` (`test_site_graph_v0_contract.py:446-453`) tests that a *declared link* must agree with the *declared hierarchy*. It does not test that the declared hierarchy agrees with anything committed.

**Fix:** in `validate_inputs`, for every `link["target_id"]` present in `node_scope_by_target`, require `link["scope_class"] == node_scope_by_target[target]` and require `link["candidate_e55_type"]` to equal the crosswalk image of that node's committed `source_types` in `baseline-node-scope.json`; append an integrity error otherwise. Candidate-authored scope may only apply to targets absent from the frozen baseline.

### P1-3 — Baseline broad-only membership is decided by a hash-order-dependent arbitrary pick, under a rule that matches neither the baseline metrics nor the candidate side

`compare_candidate.py:601-605`:

```python
if node_scope_by_target.get(next(iter(baseline_links[artifact] & base_shared)), "unclassified") == "broad"
```

`next(iter(set_of_strings))` selects an element by set iteration order, which depends on `PYTHONHASHSEED`. For a record whose shared targets are `{broad_A, unclassified_B}` the record is in `baseline_broad` or not depending on the interpreter run. Constitutional rule 2 names this exactly: "anything that depends on agent order / file iteration order / hash randomisation is a silent failure that produces non-reproducible output." The comparator's headline broad-only delta is therefore not reproducible.

It is also a third, incompatible rule. `build_baseline.scope_partition()` (`build_baseline.py:270-278`) uses precedence `specific → broad → unclassified` over the whole target set; `compare_candidate`'s `candidate_broad` (`:606-610`) uses `any(broad) and not any(specific)`. The baseline arm uses "the arbitrary first target is broad and none is specific". So `sides[m]["baseline_broad_only_conditional_share"]` (`:644`) will not even reproduce `baseline-metrics.json`'s committed `broad_only` counts, and `broad_change` (`:635-638`) subtracts two quantities computed under different definitions.

**Fix:** replace `:601-605` with the same predicate as `:606-610` (`any(... == "broad") and not any(... == "specific_candidate")`), or better, call `build_baseline.scope_partition()` for both arms so there is one definition (rule 4). Add a test asserting the comparator's baseline broad-only counts equal `baseline-metrics.json`'s `mutually_exclusive_scope_counts["broad_only"]` on the real committed data.

### P1-4 — Two committed classification authorities disagree on real baseline nodes

`build_baseline.py:31-32` hardcodes `CURRENT_BROAD_TYPES = {"administrative-unit", "archaeological-area"}` and `CURRENT_SPECIFIC_TYPES = {"archaeological-site", "populated-place", "building-institution"}`. `type-crosswalk.json:20-23` maps `hydrography`, `island`, `landcover`, `landform` to `landscape_feature` / `"scope": "broad"`.

Those four types are in neither `build_baseline` set, so they fall to `unclassified` (`build_baseline.py:117-119`). This is not hypothetical: `baseline-node-scope.json:1252-1266` classifies `idai:2042923` "Wadi Allaqui", `source_types: ["landform"]`, as `unclassified` with reason `no_frozen_scope_rule_applies`, while the frozen crosswalk says it is broad. Those are the 35 `unclassified` nodes.

`README.md:73-76` declares the crosswalk the authority ("maps all actual hyphenated iDAI types … Broad types take precedence"), and `validate_contract.py:270-279` checks only that the crosswalk's *key set* covers the types present in `raw.json` — never that the classifier agrees with the mapping. Rule 4: one fact, two places, already drifted.

The consequence compounds P1-3: a baseline record whose only shared target is a `landform` node is excluded from `baseline_broad` (class `unclassified`) but included in `candidate_broad` (the candidate's crosswalk-derived type is `landscape_feature` → broad), so `broad_change` shows a spurious increase and can flip a legitimate CONTINUE to STOP.

**Fix:** delete `CURRENT_BROAD_TYPES` / `CURRENT_SPECIFIC_TYPES` and drive `classify_current_nodes` from `type-crosswalk.json["idai_gazetteer_actual_hyphenated_types"][t]["scope"]`, raising on any type absent from the crosswalk. Re-run the two baselines and re-freeze `baseline-node-scope.json`, `baseline-metrics.json`, `planned-opportunity-queue.json` and the manifest. Add a test asserting every type in `raw.json` resolves through the crosswalk and that no node is `unclassified` for a type the crosswalk classifies.

### P1-5 — The CONTINUE effect threshold is read from an input file instead of computed, and neither the queue nor the crosswalk is bound to its preregistered hash at comparison time

`compare_candidate.py:618`: `minimum = opportunity["minimum_credited_affected_records_for_continue"]` — taken verbatim from the supplied opportunity ledger. `MINIMUM_AFFECTED_FRACTION` (`:30`) is dead: grep shows it is referenced only by `validate_contract.py:242` and the test at `:632`, never by the decision logic. The preregistered rule `max(1, ceil(0.10 * O_pair_side))` (`preregistration.json:189`) is implemented once, in `build_baseline.py:632-644`, using a *second* encoding of 1/10 (`MINIMUM_AFFECTED_NUMERATOR/DENOMINATOR`, `:26-27`). So the number the gate uses is never checked against the fraction the contract preregisters (rules 3 and 4).

Worse, nothing ties the queue file to the frozen one. `:227-230` checks `candidate["opportunity_ledger_sha256"] == sha256(paths["queue"])` — the candidate declaring the hash of whatever file it handed over. Same for `type_crosswalk_sha256` (`:229`) and `complete_hierarchy_context_sha256` (`:231`). `preregistration.json:24` and `:33` pin the real digests (`7894acc6…`, `4509d294…`), and `compare_candidate.py` never opens `preregistration.json`. A candidate author can supply a queue with smaller denominators and a crosswalk with a wider `specific_candidate` vocabulary, and the comparator will report `integrity: passed`.

That is the round-1 P1-5 failure mode moved one layer down: the queue itself is now result-blind and well-constructed, but the comparator does not require *that* queue.

**Fix:** (a) recompute `minimum = max(1, -(-opportunity["credited_effect_opportunity_denominator"] * MINIMUM_AFFECTED_FRACTION.numerator // MINIMUM_AFFECTED_FRACTION.denominator))` and append an integrity error if it disagrees with the file; (b) load `preregistration.json` in `validate_inputs` and require `sha256(paths["queue"]) == frozen_artifacts.opportunity_ledger.sha256`, `sha256(paths["crosswalk"]) == frozen_artifacts.type_crosswalk.sha256`, and both record-evidence hashes; (c) delete `MINIMUM_AFFECTED_NUMERATOR/DENOMINATOR` and import the single `Fraction`.

They control nothing. Every constraint in `schemas/candidate.schema.json:7-65` is independently re-implemented by `compare_candidate.exact_keys` (`:290-297`, `:367-369`), and `schemas/correction-ledger.schema.json` by `apply_corrections.RECORD_FIELDS` (`:22-26`). **Fix:** add `jsonschema` to the pipeline dev dependency, validate each ledger against its schema at the top of `validate_inputs` / `validate_ledger`, and add a test that the committed `evidence-corrections.json` and the logic-only comparator fixtures validate. Or delete the `schemas/` directory and stop claiming it is authoritative — but then remove the sentence at `README.md:9-11`.

### P2-2 — The review ledger does not require LLM parameters or a dated model snapshot (rule 13)

`compare_candidate.py:152-162` requires, for `method == "llm"`, prompt + raw-response artifacts with hashes, a truthy `model_selector` and a truthy `backend_model_id`. `schemas/review-ledger.schema.json:26` lists the same twelve fields. `preregistration.json:125-131` matches.

Rule 13 requires "model id + **dated snapshot**, **parameters**, the exact prompt/input, and the full raw response". There is no field for temperature/top-p/seed/max-tokens and no dated snapshot field. `backend_model_id` accepts any nonempty string, including a sentinel, with no enumerated allowed value. You held *yourselves* to the higher bar — `reviews/round-1/metadata.json:6-11` records `backend_model_snapshot`, `temperature`, `max_tokens`, `permission_mode` — but the preregistered ledger for the decisions that will actually gate credit does not require them. A decision reviewed at temperature 1.0 by an unrecorded snapshot is not replayable.

**Fix:** add `backend_model_snapshot`, `parameters` (object, required non-empty for `method == "llm"`) to `required_review` in `compare_candidate.py:110-114`, to `schemas/review-ledger.schema.json`, and to `preregistration.json:125-131`; enumerate the permitted non-exposure sentinel explicitly rather than accepting any truthy string.

### P2-3 — "credited affected records" is defined only in the comparator, and more narrowly than the preregistered wording

`preregistration.json:189` gates CONTINUE on "each side has credited affected records >= max(1, ceil(0.10 * its fixed nonempty O_pair_side))". The term is never defined in the symbol table (`:5-11`) or anywhere else. `compare_candidate.py:611-616` defines it as records whose event is `new_link` or `strict_refinement_reassignment` **and** whose candidate links intersect `gained_specific` — i.e. only records incident on targets that became *newly shared for that pair*. A record newly linked to an already-shared specific node counts zero.

That may well be the right definition, but `README.md:9-11` declares `preregistration.json` the tie-breaker over code, and `preregistration.json` does not contain it. An undefined term in a preregistration is a term that gets settled by discretion after results exist — the exact failure round 1 flagged for the held-out review.

**Fix:** add `credited_affected_record` to `preregistration.json["symbols"]` with the incident-on-gained-shared-identity condition spelled out, and assert the definition string in `test_every_machine_formula_and_decision_threshold_matches_executable_values`.

### P2-4 — The correction sensitivity path cannot show sensitivity of any headline number, and permits internally inconsistent rows

`apply_corrections.py:18-21` allows corrections to `baseline_site_target_ids` and `baseline_record_scope` as independent fields, and `:139-144` writes each correction in isolation. Correcting `baseline_site_target_ids` leaves `baseline_record_scope`, `baseline_resolution_state`, `site_mention_status_counts` and `has_blocking_ambiguity` stale — the sensitivity artifact is a record set that `build_record_rows` would have raised on (`build_baseline.py:218-221`).

`sensitivity_metrics()` (`:99-125`) then reports only `canonical_records`, `extracted_site_text_evidence_records`, `records_with_unique_site_link`, `records_with_blocking_ambiguity` and two rates. Nothing about connectivity, pair membership, node scope, or concentration — i.e. none of the numbers the contract actually decides on. `README.md:177-181` presents this as the immutable-corrections story; it is a partial one.

**Fix:** derive the sensitivity output by re-running `build_baseline.build_metrics(corrected_records, links_from_corrected_records, scope_by_target)` so the full metric surface is regenerated consistently, and either recompute the dependent fields from the corrected primitives or restrict `ALLOWED_FIELDS` to primitives only and derive the rest.

### P2-5 — The release-time report writer emits a failing report into the release tree, and no check ever reads its status

`scripts/generate_validation_report.py:19-27` calls `semantic_report()` (without `verify_release`), writes `validation-report.json` unconditionally, then exits 1 if status is `fail`. The README release sequence (`README.md:208-218`) runs `freeze_release.py --replace` immediately afterwards, which will hash whatever is on disk into the manifest.

Consequently a release can be frozen and committed containing `"status": "fail"` and still pass every automated gate: `verify_release` only checks bytes match the manifest, and neither `validate_contract.semantic_report()` nor `test_site_graph_v0_contract.py` ever reads `validation-report.json["status"]`. This is round-1 P2-1's shape surviving in the writer half.

**Fix:** in `generate_validation_report.py`, compute the report, exit non-zero *before* writing if `status != "pass"`. Add a check to `semantic_report()` asserting the committed `validation-report.json["status"] == "pass"` and, in CI, add an assertion in `test_site_graph_v0_contract.py` on that field (it is a committed file, no corpus needed).
